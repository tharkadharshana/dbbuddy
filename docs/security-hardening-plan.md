## Context

This plan was created after a full security audit of the DataMind AI backend. The findings are organised by severity and mapped to the project's MVP timeline. Items marked **[MVP BLOCKER]** must be resolved before the Phase 6 deployment readiness milestone (2026-05-30).

---

## Severity Classification

| Level | Meaning |
|-------|---------|
| **CRITICAL** | Active exploit vector or secret already exposed |
| **HIGH** | Exploitable before production launch |
| **MEDIUM** | Risk in production, not immediately exploitable |
| **LOW** | Code quality / defence in depth |

## Phase 1 — Immediate / Active Threats (Fix Now)

### SEC-01 · Exposed DeepSeek API Key `[CRITICAL]` `[MVP BLOCKER]`

**File:** `datamind/backend/.env` line 58  
**Finding:** A real `DEEPSEEK_API_KEY` value is present in `.env`. If this file has ever been committed to git or shared, the key is compromised.

**Action (manual — cannot be automated):**
1. Check git history: `git log --all --full-history -- datamind/backend/.env`
2. If the file appears in history, the key is already leaked — rotate it at https://platform.deepseek.com immediately.
3. Add `.env` to `.gitignore` if not already present.
4. Use `.env.example` with placeholder values only.

**Status:** ⏳ Requires manual key rotation by developer.

---

### SEC-02 · Error Responses Leak Internal Details `[CRITICAL]` `[MVP BLOCKER]`

**Files:** `datamind/backend/main.py` — ~15 locations  
**Finding:** `raise HTTPException(status_code=500, detail=str(e))` exposes raw Python exception strings to API clients. These can contain DB hostnames, file paths, SQL syntax errors, and internal library details.

**Fix:** Replace `str(e)` in all HTTP responses with a generic message. Log the full error server-side. Introduce a `_http_error()` helper.

```python
def _http_error(status: int, public_msg: str, exc: Exception = None) -> HTTPException:
    if exc:
        log.error(public_msg, error=str(exc), exc_info=True)
    return HTTPException(status_code=status, detail=public_msg)
```

**Affected locations:**
- `/onboarding/test-connection` → 484
- `/tables/{table_name}/columns` → 771
- `/query` → 1021
- `/forecast` → 1227
- `/forecast/auto` → 1306
- `/anomalies` → 1355
- `/anomalies/auto` → 1397, 1432
- `/integrations/{provider_id}/forecast` → 1887
- Many others

**Status:** ✅ Fixed in this branch.

### SEC-03 · Integration Forecast SQL Injection `[CRITICAL]` `[MVP BLOCKER]`

**File:** `datamind/backend/main.py` lines 1862–1865  
**Finding:** The `/integrations/{provider_id}/forecast` endpoint uses `req.date_column`, `req.value_column`, and `req.table` directly in an f-string SQL query with no backtick quoting and no schema validation.

```python
# VULNERABLE — no backticks, no _validate_table_column
cursor.execute(
    f"SELECT DATE({req.date_column}) as date, SUM({req.value_column}) as value "
    f"FROM {table_prefix}_{req.table} "
    ...
)
```

**Fix:** Add `_validate_table_column()` calls (already exists in the codebase) and wrap identifiers in backticks.

**Status:** ✅ Fixed in this branch.

---

### SEC-04 · LLM-Generated SQL Executed Without Mutation Guard `[HIGH]` `[MVP BLOCKER]`

**File:** `datamind/backend/main.py` line 1007  
**Finding:** SQL generated by the LLM (Gemini/DeepSeek) is executed directly:
```python
cursor.execute(sql)  # sql came from LLM
```
The system prompt instructs the LLM not to write mutating queries, but this is not enforced in code. A compromised API key, prompt injection via user data, or a hallucinating model could generate `DROP TABLE`, `DELETE`, or `UPDATE` statements.

**Fix:** Add a `_guard_sql()` function that raises a 400 error if the generated SQL contains any DML/DDL mutation keywords before execution.

**Status:** ✅ Fixed in this branch.

## Phase 2 — Pre-Production Hardening (Fix Before 2026-05-30)

### SEC-05 · Weak JWT Secret Key Fallback `[HIGH]` `[MVP BLOCKER]`

**File:** `datamind/backend/auth.py` line 15  
**Finding:**
```python
SECRET_KEY = os.getenv("SECRET_KEY", "datamind-secret-change-in-production-2024")
```
If `SECRET_KEY` is not set in production, all JWTs are signed with a well-known hardcoded string, making them forgeable by anyone who reads this source code.

**Fix:** Emit a loud `WARNING` at startup if the default key is in use. In a future iteration, raise `RuntimeError` in production mode.

**Status:** ✅ Fixed in this branch (startup warning added).

---

### SEC-06 · DB Passwords Stored in Plaintext `[HIGH]` `[MVP BLOCKER]`

**File:** `datamind/backend/main.py` lines 499–502 (and `auth.py` via `update_user_settings`)  
**Finding:** User-provided database passwords (host, user, password) are stored as plain JSON in the `users.settings` MySQL column. Integration credentials use Fernet encryption (`integrations.py`), but DB configs do not.

**Fix:** Encrypt the `password` field in `db_configs` using the same Fernet key already present in `integrations.py`. Decrypt on read before passing to `get_connection()`.

**Migration concern:** Existing saved configs will have plaintext passwords. The decryption helper must detect plaintext (non-base64 token) and re-encrypt on first read.

**Status:** ✅ Fixed in this branch.

---

### SEC-07 · CORS Defaults to `*` When Env Var Unset `[HIGH]` `[MVP BLOCKER]`

**File:** `datamind/backend/main.py` lines 74–79  
**Finding:**
```python
_cors_origins = (
    ["http://localhost:5173", "http://localhost:3000"] + _embed_origins
    if _embed_origins else ["*"]   # ← allows any origin
)
```
Any website can make credentialed requests to the API if `EMBED_ALLOWED_ORIGINS` is not set.

**Fix:** Change default to `["http://localhost:5173", "http://localhost:3000"]` always. Only append embed origins when provided. Never default to `"*"`.

**Status:** ✅ Fixed in this branch.

---

### SEC-08 · Standard Error Envelope `[MEDIUM]` (Timeline: M1 · 2026-05-21)

**Finding:** API errors have inconsistent shapes — some return `{"ok": False, "error": "..."}`, others raise `HTTPException` with `{"detail": "..."}`. Frontend must handle both cases. This is already in the M1 milestone backlog.

**Fix:** Introduce a FastAPI exception handler that normalises all 4xx/5xx responses to:
```json
{"ok": false, "error": "Human-readable message", "code": "ERROR_CODE"}
```

**Status:** ✅ Fixed in this branch (global exception handler added).

---

### SEC-09 · Encryption Key Derived via Raw SHA-256 `[MEDIUM]`

**File:** `datamind/backend/integrations.py` lines 39–47  
**Finding:** The Fernet encryption key is derived from `SECRET_KEY` using `hashlib.sha256()` — not a proper key derivation function. This is acceptable for now but should be upgraded.

**Fix (post-MVP):** Migrate to PBKDF2HMAC or Argon2. This requires a one-time re-encryption migration of all stored credentials. Defer to M3 infrastructure phase.

**Status:** ⏳ Deferred — post-MVP (2026-06-13+).

---

### SEC-10 · Missing Rate Limiting on Auth Endpoints `[MEDIUM]`

**File:** `datamind/backend/main.py` — `/auth/register`, `/auth/login`  
**Finding:** No rate limiting. Allows brute-force password attacks and account enumeration.

**Fix:** Add `slowapi` middleware with per-IP rate limits on auth endpoints (e.g., 10 req/min on login).

```bash
pip install slowapi
```

**Status:** ⏳ Pending — schedule for Phase 6 stabilisation (2026-05-30).

### SEC-11 · User Data Isolation — FK Prefix Collision Risk `[MEDIUM]`

**File:** `datamind/backend/main.py` lines 994–1002  
**Finding:** Foreign key filtering for integration users uses prefix-based matching. If two users have overlapping table prefixes (e.g., `sales_` and `sales_detail_`), User A's LLM prompt could contain User B's FK relationships.

**Current state:** The code at line 959–976 queries `information_schema.TABLES WHERE TABLE_NAME LIKE '{prefix}%'` which already scopes to exact prefix — this limits the risk significantly. The FK filter at 995–1000 then cross-checks both sides against `user_tables`.

**Remaining risk:** Only exists if two users are assigned identical or prefix-overlapping table prefixes by the integration bootstrap. Table prefixes are generated from a hash of (email, provider, timestamp) — collision is unlikely but not impossible.

**Fix (post-MVP):** Add a `UNIQUE` constraint on the `table_prefix` column in the integrations table. Log a warning at bootstrap time if a collision is detected.

**Status:** ⏳ Deferred — post-MVP.

## Phase 3 — LLM Context Hardening (Post-MVP)

### SEC-12 · Full Database Schema Sent to External LLM `[HIGH → MEDIUM after scoping fix]`

**File:** `datamind/backend/llm.py` lines 283–306 (`query_to_sql`)  
**Finding:** The entire schema is sent to Gemini/DeepSeek on every NL query. This means column names (which may reflect business-sensitive or PII-adjacent naming like `customer_ssn`, `loyalty_points`) are transmitted to a third-party provider.

**Current mitigations already in place:**
- For integration users, schema is already scoped to that user's tables only (lines 988–1002).
- For own-DB users, schema is scoped to the connected DB only.

**Remaining concern:** The schema includes all column names and types — there is no column-level filtering.

**Fix (post-MVP):**
1. Add a column allow-list in the cache that excludes columns matching sensitive patterns (`password`, `hash`, `secret`, `token`, `ssn`, `cvv`).
2. Consider schema summarisation: send table/column descriptions, not raw DDL.

**Status:** ⏳ Deferred — post-MVP.

---

### SEC-13 · Sample Data Sent to LLM During Cache Build `[HIGH]`

**File:** `datamind/backend/schema_builder.py` lines 195–216  
**Finding:** Actual row values (sample data) are sent to the LLM during schema cache build. This data could contain PII (names, emails, phone numbers, transaction details).

**Fix (post-MVP):**
1. Replace sample data with column statistics only (min, max, count, distinct count).
2. Or: hash/mask PII-looking column values before sending.

**Status:** ⏳ Deferred — post-MVP (high impact change, requires schema builder rewrite).

## Phase 4 — Infrastructure (Aligned with M3)

### SEC-14 · No HTTPS Enforcement `[MEDIUM]`

**Finding:** Backend has no HTTPS redirect or HSTS header. JWT tokens and DB passwords are transmitted over HTTP in non-SSL environments.

**Fix:** Configure TLS termination at the reverse proxy (nginx/ALB). Add HSTS header middleware.

**Status:** ⏳ Deferred — infrastructure phase (2026-06-13+).

---

### SEC-15 · DEBUG Log Level in Production `[MEDIUM]`

**File:** `datamind/backend/.env` line 85  
**Finding:** `LOG_LEVEL=DEBUG` enables verbose logging. In production, this risks logging sensitive request context.

**Fix:** Set `LOG_LEVEL=INFO` in production `.env`. Add to deployment checklist.

**Status:** ⏳ Pending — deployment readiness (2026-05-30).

### SEC-16 · MySQL `my.cnf` Tuning `[MEDIUM]` (Timeline: M2 · 2026-05-26)

**Finding:** Already on the M2 roadmap. Relevant security settings to include:
- `bind-address = 127.0.0.1` (no external MySQL exposure)
- `local_infile = 0` (disable `LOAD DATA LOCAL INFILE`)
- `skip_symbolic_links = 1`
