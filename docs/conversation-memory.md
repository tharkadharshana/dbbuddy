# Conversation Memory — Implementation Plan

## Problem Being Solved

The chat system (`/v1/query`) is completely stateless. Every message is an
independent NL→SQL query with no knowledge of previous exchanges. This causes:

1. **Follow-up questions fail** — "explain this value" generates fresh SQL
   (a broad SELECT *) instead of referencing the previous result.
2. **No conversation history** — users cannot revisit past analysis sessions.
3. **No context awareness** — the LLM cannot reason across multiple turns.
4. **Keyword hacks don't work** — hardcoding trigger words ("explain", "why")
   is fragile and still requires a new SQL query.

## Solution

Each chat session becomes a **conversation thread** — a persistent, addressable
object stored in the database. Every new message in that thread sends a
compact history of previous exchanges to the LLM so it always has full context.

This is the same model used by ChatGPT, Claude, and every modern AI chat
product. The LLM naturally handles follow-ups, clarifications, and topic
changes without any keyword detection.

## Database Schema

Three new tables added to the DataMind internal DB via `_bootstrap_db()` in
`datamind/backend/integrations.py`.

### `conversations`

```sql
CREATE TABLE IF NOT EXISTS conversations (
    id           VARCHAR(64)  NOT NULL,
    user_email   VARCHAR(255) NOT NULL,
    title        VARCHAR(255) DEFAULT 'New conversation',
    summary      TEXT,
    message_count INT         DEFAULT 0,
    created_at   DATETIME     DEFAULT NOW(),
    updated_at   DATETIME     DEFAULT NOW(),
    PRIMARY KEY (id),
    INDEX idx_user_updated (user_email, updated_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
```

- `id` — UUID generated by the frontend on conversation creation.
- `title` — initially "New conversation", replaced by LLM-generated title
  after the first exchange completes (async, non-blocking).
- `summary` — LLM-generated paragraph summary of the full thread, written
  after the 20th message and updated every 5 messages thereafter.
- `message_count` — denormalised counter, incremented on each insert.
  Avoids a COUNT(*) on conversation_messages for list views.

### `conversation_messages`

```sql
CREATE TABLE IF NOT EXISTS conversation_messages (
    id              BIGINT       NOT NULL AUTO_INCREMENT,
    conversation_id VARCHAR(64)  NOT NULL,
    role            VARCHAR(16)  NOT NULL,  -- 'user' | 'assistant'
    content         TEXT         NOT NULL,  -- question or answer summary text
    sql_query       TEXT,                   -- generated SQL (nullable)
    row_count       INT          DEFAULT 0,
    data_snapshot   JSON,                   -- col names + first 10 rows + stat line
    created_at      DATETIME     DEFAULT NOW(),
    PRIMARY KEY (id),
    INDEX idx_conv_created (conversation_id, created_at),
    FOREIGN KEY (conversation_id)
        REFERENCES conversations(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
```

- `content` for user messages: the raw question text.
- `content` for assistant messages: the answer summary
  ("Found 10 results. Total revenue: $44,991,596.55").
- `data_snapshot`: a compact JSON object — **NOT the full result set**.
  Format: `{"columns": [...], "rows": [[...], ...], "stat": "SUM=44991596.55"}`.
  Capped at 10 rows. This is what gets sent back to the LLM on follow-ups —
  enough context without burning thousands of tokens on raw data.
- `sql_query`: stored for debugging and audit. Not sent to the LLM.

### `conversation_summaries`

```sql
CREATE TABLE IF NOT EXISTS conversation_summaries (
    id              BIGINT       NOT NULL AUTO_INCREMENT,
    conversation_id VARCHAR(64)  NOT NULL,
    summary_text    TEXT         NOT NULL,
    covers_up_to_id BIGINT       NOT NULL,  -- messages up to this ID are compressed
    created_at      DATETIME     DEFAULT NOW(),
    PRIMARY KEY (id),
    INDEX idx_conv (conversation_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
```

When a conversation grows beyond 20 messages, the oldest messages are
summarised into a paragraph and stored here. Future requests send
`[summary paragraph] + last 5 messages` instead of the full history.
Keeps token cost bounded regardless of conversation length.

## API Endpoints (added to `main.py`)

All under `/v1/conversations`, auth-gated with `current_user`.

```
POST   /v1/conversations
       Body: { "id": "uuid-generated-by-frontend" }
       Creates a new conversation. Returns the conversation row.
       Rate limit: WRITE tier.

GET    /v1/conversations
       Returns list of user's conversations (id, title, message_count, updated_at).
       Most recent first. Limit 50.
       Rate limit: READ tier.

GET    /v1/conversations/{conv_id}/messages
       Returns full message list for a conversation.
       Ownership enforced — 404 if not owner.
       Rate limit: READ tier.

DELETE /v1/conversations/{conv_id}
       Deletes conversation + all messages (CASCADE).
       Ownership enforced.
       Rate limit: WRITE tier.
```

## Changes to `/v1/query`

### New request fields

```python
class NLQueryRequest(BaseModel):
    question:        str
    llm:             str  = "gemini"
    think_mode:      bool = False
    conversation_id: str  = None   # NEW — optional, fully backward compatible
```

### New flow when `conversation_id` is provided

```
1. Load history via get_history_with_summary(conversation_id)
   → (summary | None, list of last N messages)

2. Build history_prompt string via build_history_prompt(summary, messages)

3. Pass history_prompt to query_to_sql() as new parameter

4. query_to_sql() prepends history to the system prompt:
   "You are an expert MySQL query writer...
    [Previous conversation context]:
    User: What was my total revenue last month?
    Assistant: Found 1 result. total_revenue_last_month = 44991596.55
    [Data: columns=[total_revenue_last_month], sample=[[44991596.55]], stat=SUM=44991596.55]

    Current question: explain this value"

5. LLM understands "this value" = $44,991,596.55 from the previous exchange.
   It can now either:
   a. Generate a focused SQL query to drill deeper, OR
   b. Directly explain based on the data_snapshot in history (no new SQL needed)

6. After response, save both messages to conversation_messages:
   - save_message(conv_id, "user", question)
   - save_message(conv_id, "assistant", answer_summary, sql, row_count, snapshot)

7. If message_count == 1: trigger async title generation (non-blocking thread)
8. If message_count % 5 == 0 and message_count >= 20: trigger async summarisation
```

### Backward compatibility

If `conversation_id` is `None` (old clients, embed users), the endpoint
behaves exactly as before — no history loaded, no messages saved. Zero
breaking changes.

```python
    history_section +
    "You are an expert MySQL query writer. "
```

Triggered after the first assistant message is saved (message_count becomes 2).

```python
def _generate_conversation_title(conv_id, first_question, first_answer,
                                  llm, api_key, user_email):
    prompt = (
        f"Generate a short title (max 8 words) for a conversation that started with:\n"
        f"Question: {first_question}\n"
        f"Answer: {first_answer}\n"
        f"Title only, no punctuation, no quotes."
    )
    title = call_llm(prompt, ..., max_tokens=30)
    update_title(conv_id, title.strip())
```

Run in a `threading.Thread(daemon=True)` so it doesn't block the response.

## Token Cost Analysis

| Scenario | Tokens per request | vs. today |
|---|---|---|
| First message (no history) | ~2,500 | same |
| 5-message conversation | ~3,200 | +700 |
| 10-message conversation | ~4,000 | +1,500 |
| 20+ message (with summary) | ~3,500 | +1,000 |

The data_snapshot (10 rows max per message) keeps history compact.
A 10-message conversation adds roughly 1,500 tokens — about $0.001 on
DeepSeek. Acceptable cost for the benefit.

## Implementation Order

1. DB schema (`integrations.py`) — foundation everything else depends on
2. `conversations.py` — all DB logic in one place
3. Backend API endpoints (`main.py`) — CRUD for conversations
4. Update `/v1/query` — inject history, save messages
5. Update `query_to_sql()` (`llm.py`) — accept history string
6. Background title + summarisation jobs
7. Frontend `api.js` — new API calls
8. Frontend `App.jsx` — conversation state
9. `ConversationSidebar.jsx` — new component
10. `ChatPage.jsx` — wire everything together

Each step is committed separately.
